## 2. 产品说明计划书（必交）

正文用 `docs/产品说明计划书.md`（四项齐全 + 界面截图）。
若表单是**文本框**而非附件，按下面四段精简粘贴（每段 300–600 字）：

**① 核心创作思路**
```
知面陪练解决的是面试/答辩里的"输入-输出断层"：读懂了却讲不清，一被追问就卡壳。
现有八股题站给的是答案不是训练，AI 对话框给的是客气。我们用知乎真实高赞语料做底，
把闭环做成"读懂 → 说清 → 被追问 → 查清楚"：先给考察意图与 3 个核心得分点（拆逻辑），
再由评委顺着你的回答逐层追问（模拟练），最后逐句回指原话给出可核对的改进话术（看复盘），
并把最佳作答提炼成闪卡沉淀进弹药库。三条壁垒：知乎语料逐字可溯源、每条结论必须挂来源编号、
服务端零落盘（所有个人数据只存在评委自己的浏览器里）。
```

**② 技术实现**
```
原生 ES Module SPA + Node(Hono) BFF，同域单端口同时托管静态站与 API（规避 CORS，录音需安全上下文）。
服务端零落盘：录音/转写稿/简历/复盘/闪卡全在浏览器 IndexedDB，部署无状态、可随时迁移。
诊断采用"确定性规则层(10 条原话级诊断) + 模型层(结构化评分与追问)"双轨：模型结论必须挂到来源编号，
越界或无依据引用被丢弃并计数，无来源的题目显式降级为规则模式，绝不编造。
长耗时调用走 SSE 流式返回阶段文案；模型调用层有并发闸门(默认3)、超时/5xx 重试、客户端断连中断上游、用量统计。
数据备份带 schema 版本，导入时校验并迁移；公网可用分享口令(x-share-token)防止额度被白用。
题库 92 道真实知乎题（7 个方向、难度三档）、316 张观点卡，evidence 逐字校验 316/316 通过。
前端冒烟 9 条 + 后端单测 11 条 + strict 类型检查 0 错。
```

**③ 与知乎社区生态的契合度**
```
题库全部来自知乎真实提问，观点卡全部来自知乎真实回答并逐字校验，界面上每条观点可一键打开知乎原文 ——
我们把知乎长回答压缩成"可背诵的 3 步框架"，是知乎内容在求职/答辩场景的二次分发。
全程使用知乎开放平台（推荐/回答/搜索）作为唯一内容来源，并遵守每日配额、熔断与磁盘缓存策略。
可选接入知乎 OAuth（顶栏显示身份），但不设登录墙，评委打开即用。
```

**④ 场景价值与后续落地设想**
```
面向校招/社招求职者（按自己简历出题、评委顺着你的回答追问）、毕设/开题学生（预演评委对方法边界与
对照实验的质疑）、团队内部演练（用团队自己的材料生成刁钻问题清单）。后续：题库持续供给与按使用数据排序、
把闪卡做成可协作的团队知识卡组、做成浏览器插件在面试当下查话术、把高频追问反哺成知乎问答专题、
本地优先架构可复用到企业内部面试系统（简历不出内网）。
```
